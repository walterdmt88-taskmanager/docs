# IRD-005 — notification-service

**Scope:** Async event consumption from Redis Streams and Discord webhook delivery.
**Linked DOP:** DOP-001 — observability and team awareness requirement
**Depends on:** Redis (`task:events` stream published by task-service)
**Does NOT receive traffic from:** api-gateway (internal consumer only)

---

## What this service does

`notification-service` is a background consumer. It has no public API surface.
It subscribes to the `task:events` Redis Stream using a consumer group and sends
rich Discord embed notifications whenever a task is created, its status changes,
or a comment is posted.

The HTTP server (Express) exists only to expose `/health` for Kubernetes liveness probes.

## Consumer group behavior

- Consumer group is created with `XGROUP CREATE ... $ MKSTREAM` on startup (idempotent).
- Uses `XREADGROUP ... BLOCK 5000` — waits up to 5 seconds for new messages per iteration.
- Acknowledges (`XACK`) each message immediately after Discord delivery attempt.
- If Discord call fails, the message is still acknowledged (best-effort delivery — no retry loop to avoid spamming Discord on transient errors).
- If Redis is unreachable at startup, the consumer loop retries every 2 seconds.

## Failure modes

| Failure | Impact | Behaviour |
|---|---|---|
| Redis down at startup | No notifications | Consumer retries every 2s |
| Redis down mid-run | No notifications until reconnect | ioredis auto-reconnects |
| Discord webhook fails | Notification dropped | Logged, message acknowledged |
| notification-service pod crashes | Notifications paused | K8s restarts pod; consumer group re-delivers un-acked messages |
| task-service Redis publish fails | Notification never sent | Logged, task operation still succeeds |
