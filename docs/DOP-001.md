## Problem statement

Teams tracking tasks in chat tools (Slack, Discord) lose context — tasks get buried in messages, ownership is unclear, and there is no way to see what is blocked or overdue. This system gives teams a central place to create, assign, and track tasks via a REST API, with a clear audit trail of who did what and when.

## Users and use cases

### Team Member
The primary user. Creates tasks, gets assigned tasks, updates task status.

| Use case | Description |
|---|---|
| Register an account | Provide email + password + full_name → receive a user account |
| Log in | Provide credentials → receive a JWT token |
| Create a task | Provide title, description, assignee → task is saved |
| Update task status | Move a task from `TODO` → `IN_PROGRESS` → `DONE` |
| Add a comment | Attach a text comment to any task |
| View my tasks | List all tasks assigned to me, filterable by status |
| Log in via web UI | Open the browser app, enter credentials, access the task dashboard |
| View tasks in browser | See their assigned tasks in a web page, filter by status |
| Create a task via form | Fill in a web form to create a task without writing any API calls |
| Update status in browser | Click to change a task's status directly in the web UI |
| Add a comment in browser | Submit a comment via a form on the task detail page |

### Team Lead
Extends Team Member. Has read access to all tasks regardless of assignee.

| Use case | Description |
|---|---|
| View all tasks | List all tasks in the system, filter by status or assignee |
| View overdue tasks | List tasks still `todo` or `in_progress` past their due date |
| Dashboard in browser | See all tasks across all assignees in the web UI with status filters |

## Services and ownership

Each service owns its data completely. No service reads another service's database directly.

### user-service
**Owns:** user accounts, credentials, JWT issuance  
**Does NOT own:** tasks, comments, or any application data  
**Exposes:** `POST /users` (register), `POST /auth/login` (login)
> ⚠️ **AUDIT GAP (2026-05-15):** Code also exposes `GET /users/:id` (get single user) and `GET /users/` (list all users). These routes are not documented here. Add them or confirm they are internal-only.

### task-service
**Owns:** tasks, task status, task comments  
**Does NOT own:** user profiles (stores only `user_id` references)  
**Exposes:** full CRUD on `/tasks`, `POST /tasks/:id/comments`

### api-gateway
**Owns:** routing, JWT validation middleware, CORS headers  
**Does NOT own:** any business data — it delegates to services  
**Rule:** all client requests go through the gateway. Services do not expose ports to the outside directly.

### frontend-service
**Owns:** the compiled React SPA (static HTML/JS/CSS)  
**Does NOT own:** any data — all state lives in user-service and task-service  
**Served by:** nginx alpine Docker container on port 3000  
**Connects to:** api-gateway at `:8080` (browser makes all API calls directly to the gateway)

### db-user (infrastructure)
**Owns:** user data persistence (PostgreSQL 15)
**Exposed to:** user-service only, not reachable from outside app-net network

### db-task (infrastructure)
**Owns:** task and comment data persistence (PostgreSQL 15)
**Exposed to:** task-service only, not reachable from outside app-net network

### redis (infrastructure — K8s only)
**Owns:** rate-limit counters for api-gateway  
**Deployed via:** Helm chart `bitnami/redis`, release name `my-redis`  
**Note:** Redis is NOT in docker-compose — rate limiting is K8s-environment only
> ⚠️ **AUDIT GAP (2026-05-15):** Redis Helm values exist (`k8s/taskmanager/my-redis-values.yaml`) but api-gateway has NO rate-limit middleware implemented. AC-14 is unmet. See below.

## Acceptance criteria

Each criterion is the source for one User Story in the sprint backlog.

| ID | Given | When | Then |
|---|---|---|---|
| AC-01 | A new user provides a valid email, password, and full_name | They call `POST /users` | A user account is created. The response includes `id`, `email`, `full_name`, `role`, `created_at`. No `password_hash`. Status 201. |
| AC-02 | A registered user provides correct credentials | They call `POST /auth/login` | A signed JWT is returned with `userId` in the payload. Expires in 24h. Status 200. |
| AC-03 | An authenticated user provides title, description, and `assignee_id` | They call `POST /tasks` | A task is created with status `todo`. The response includes the full task object. Status 201. |
| AC-04 | An authenticated user provides a valid `status` value | They call `PATCH /tasks/:id/status` | The task status is updated. Invalid status values return 400 with a message listing valid values. |
| AC-05 | An authenticated user provides comment text | They call `POST /tasks/:id/comments` | The comment is saved and returned. Status 201. |
| AC-06 | An authenticated member requests their tasks | They call `GET /tasks` | All tasks where `assignee_id` or `created_by` matches the caller are returned, ordered by `created_at` desc. No query param needed — the service filters by role automatically. |
| AC-07 | An authenticated team lead requests all tasks | They call `GET /tasks` | All tasks in the system are returned. Non-leads calling this endpoint without filters get only their own tasks. |
| AC-08 | A registered user opens the web app | They visit `/login` and submit credentials | They are authenticated, a JWT is stored client-side, and they are redirected to the task dashboard. |
| AC-09 | An authenticated user opens the task dashboard | The page loads at `/` | Their assigned tasks are listed with status badges, ordered by `created_at` desc. A team lead sees all tasks. |
| AC-10 | An authenticated user fills in the create-task form | They submit title + description + assignee | A task is created, the list refreshes, and the new task appears at the top. |
| AC-11 | An authenticated user is on a task detail page | They select a new status from the status selector | The task's status is updated immediately in the UI. Invalid transitions show an error. |
| AC-12 | An authenticated user is on a task detail page | They submit the add-comment form | The comment appears in the comment list without a full page reload. |
| AC-13 | An authenticated team lead opens the task dashboard | They apply an assignee or status filter | The list refreshes to show only tasks matching the selected filter. |
| AC-14 | Any client calls `POST /auth/login` more than 10 times per minute from the same IP | The 11th request within the window arrives | The gateway returns HTTP 429 `{ "error": "Too many requests, retry after 60s" }`. Counter stored in Redis (Helm-installed, release: my-redis). |

> ⚠️ **AUDIT GAP (2026-05-15): AC-14 NOT IMPLEMENTED.** `api-gateway/src/app.ts` has no rate-limit middleware. `my-redis-values.yaml` exists but the client-side code was never written. This AC must be implemented before CI/CD week gates are added.
