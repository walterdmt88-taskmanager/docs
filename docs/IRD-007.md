## Objective

Every Kubernetes Deployment and StatefulSet in this project must conform to these standards. No manifest is merged unless all rules pass. These rules are the minimum bar — they are not optional even in training environments.

---

## Rule 1 — Resource Requests and Limits Are Mandatory

Every container in every Deployment and StatefulSet must declare both `requests` and `limits`.

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

**Why required:** Without resource limits, one misbehaving container can starve all other Pods on the node. The K8s scheduler cannot make placement decisions without `requests`. Running without limits in a shared cluster is a security risk (resource exhaustion attack surface).

**Validation:** `grep -r "resources:" k8s/taskmanager/` must return a match for every Deployment and StatefulSet file.

---

## Rule 2 — Liveness and Readiness Probes Are Mandatory

Every container in every Deployment must configure both `livenessProbe` and `readinessProbe`.

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 3001
  initialDelaySeconds: 15
  periodSeconds: 20
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /health
    port: 3001
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3
```

**Why required:**
- `readinessProbe`: K8s will not route traffic to a Pod until readiness passes. Without it, the Pod receives requests before the app is ready → connection refused errors on deployment.
- `livenessProbe`: K8s restarts Pods that fail liveness. Without it, a deadlocked process runs forever consuming a slot and never recovering.

**Defaults (per service):**

| Service | Liveness path | Port |
|---------|--------------|------|
| api-gateway | `/health` | 8080 |
| user-service | `/health` | 3001 |
| task-service | `/health` | 3002 |
| frontend-service | `/` | 3000 |
| db-user / db-task | TCP check on 5432 | 5432 |

For StatefulSets (databases): use `tcpSocket` probe instead of `httpGet`.

```yaml
livenessProbe:
  tcpSocket:
    port: 5432
  initialDelaySeconds: 30
  periodSeconds: 10
```

## Rule 3 — Namespace Policy

**Rule:** All resources in this project deploy to the `default` namespace.

```yaml
metadata:
  namespace: default
```

**Rationale:** Training environment uses a single namespace to reduce cluster management overhead. Production systems would use dedicated namespaces per team/env. Explicitly specifying `namespace: default` prevents accidental deployment to a wrong namespace when `kubectl` context changes.

**Exception:** Helm-managed releases (bitnami/redis) install into `default` via `--namespace default` flag.

## Rule 4 — ConfigMap and Secret Injection Rules

| Source | For | Method | Example |
|--------|-----|--------|---------|
| `ConfigMap` | Non-sensitive env vars (DB host, port, service URLs) | `envFrom.configMapRef` | `DATABASE_HOST`, `REDIS_HOST` |
| `Secret` | Sensitive values (passwords, JWT keys) | `envFrom.secretRef` | `DATABASE_URL`, `JWT_SECRET`, `POSTGRES_PASSWORD` |

**Rule:** Sensitive values must come from Secrets, never ConfigMaps. The distinction is not just policy — Secrets can be encrypted at rest in etcd; ConfigMaps cannot.

**Creation method:** Secrets are created via `kubectl create secret generic` only. Never committed as YAML with real values.

```bash
# Correct — imperative creation
kubectl create secret generic user-svc-secret \
  --from-literal=DATABASE_URL="postgres://..." \
  --from-literal=JWT_SECRET="..."

# NEVER — committed YAML with real values
# (any grep for "password:" in k8s/ must return zero real values)
```

## Rule 5 — Replica Count Policy

| Service type | Min replicas | Notes |
|--------------|-------------|-------|
| Stateless service (api-gateway, user-service, task-service, frontend) | 2 | High availability; allows rolling update with 0 downtime |
| StatefulSet (db-user, db-task) | 1 | Single PostgreSQL instance; HA via PVC persistence, not replicas |
| Redis (Helm) | 1 master | Rate-limit counter; Helm values set `architecture: standalone` |

---

## Rule 6 — Rolling Update Strategy

All Deployments use rolling update (K8s default). Do not override with `Recreate` unless there is a documented reason.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

`maxUnavailable: 0` ensures zero downtime deploys — new Pod must be Ready before old Pod is terminated.

## Audit Checklist

Run before every PR that touches `k8s/taskmanager/`:

- [ ] Every Deployment/StatefulSet file has `resources.requests` and `resources.limits`
- [ ] Every Deployment container has `livenessProbe` and `readinessProbe`
- [ ] All resources specify `namespace: default`
- [ ] No Secret YAML files contain real values — `grep -r "password:" k8s/` returns zero real values
- [ ] StatefulSets use `tcpSocket` probe, not `httpGet`
- [ ] Stateless services have `replicas: 2`
