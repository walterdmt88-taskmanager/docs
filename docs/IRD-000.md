**Scope:** Cross-cutting rules that apply to ALL services in this project.

**Read this before reading any service IRD.**

## 1. Error Response Format

All error responses across all services use this shape — no exceptions:

```json
{ "error": "human-readable string" }
```

**Rules:**
- Never return `{ "message": "..." }` — always `{ "error": "..." }`
- Never include stack traces, file paths, or SQL in production responses
- Never nest the error: `{ "error": { "detail": "..." } }` is wrong
- The string must be human-readable — not an error code like `ERR_EMAIL_DUPLICATE`

## 2. JWT Payload Standard

JWTs are signed by user-service and validated by api-gateway.

**Signed payload:**
```json
{
  "sub":  "<user UUID>",
  "role": "member | lead",
  "iat":  <unix timestamp>,
  "exp":  <unix timestamp>
}
```

**Rules:**
- Use `sub` (JWT standard) for the user ID — never `userId`, never `id`
- Do NOT include `email` in the token — it is not needed downstream
- `role` is either `"member"` or `"lead"` — lowercase strings
- Algorithm: HS256. Expiry: 24h (`JWT_EXPIRES_IN=24h`)
- `JWT_SECRET` must be identical in user-service and api-gateway — managed as a single env var

## 3. Date and Time Format

All timestamps in API responses use **ISO 8601 UTC**:

```
"2026-04-09T08:00:00.000Z"
```

**Rules:**
- Always UTC — never local time, never Unix timestamp in responses
- PostgreSQL `TIMESTAMPTZ` columns serialise to ISO 8601 automatically via `pg` library
- Date-only fields (e.g. `due_date`) use `YYYY-MM-DD` format
- Never return raw PostgreSQL `Date` objects — always serialise to string

---

## 4. Status Values

Task status values are uppercase strings stored in PostgreSQL CHECK constraints:

```
TODO  ·  IN_PROGRESS  ·  DONE  ·  CANCELLED
```

**Rules:**
- Always uppercase in DB, API responses, request bodies, and test assertions
- Never use lowercase (`todo`, `in_progress`) anywhere in code or docs
- Transitions: TODO→IN_PROGRESS→DONE (terminal). Any→CANCELLED (terminal). No backward.
- Invalid transition: `400 { "error": "Invalid status transition" }`
- Invalid value: `400 { "error": "status must be one of: TODO, IN_PROGRESS, DONE, CANCELLED" }`

## 5. Health Check

Every service must implement:

```
GET /health  →  200
{ "status": "ok", "service": "<service-name>" }
```

**Rules:**
- No authentication required
- Service name matches the repo name: `"user-service"`, `"task-service"`, `"api-gateway"`, `"frontend-service"`
- Used by Docker health checks — must respond within 5s
- frontend-service implements this in nginx (not Node.js)

## 6. Configuration — Environment Variables

```
.env          ← gitignored — contains real values — never committed
.env.example  ← committed — contains keys with empty values — documents what is needed
```

**Rules:**
- Zero hardcoded config: no ports, URLs, secrets, or DB passwords in source code
- All config via environment variables only
- `.env.example` must be kept in sync with `.env` — every key in `.env` must appear in `.env.example`
- Never commit `.env` — if it appears in `git status`, stop and check `.gitignore`

## 7. Database Conventions

**Naming (snake_case everywhere):**

| Object | Convention | Example |
|--------|-----------|---------|
| Table names | `snake_case`, plural | `users`, `tasks`, `comments` |
| Column names | `snake_case` | `created_at`, `assignee_id`, `password_hash` |
| Index names | `idx_<table>_<column>` | `idx_users_email`, `idx_tasks_status` |
| Migration files | `NNN_<verb>_<table>.sql` | `001_create_users.sql`, `002_create_tasks.sql` |

**UUID standard:**
- Primary keys: UUID v4 via PostgreSQL `gen_random_uuid()` — DB generates, not application
- Requires: `CREATE EXTENSION IF NOT EXISTS "pgcrypto";` at top of migration
- Cross-service references: store UUID only — no foreign keys across service boundaries

**Migrations:**
- Location: `db/migrations/` in each service repo
- Naming: zero-padded sequence + verb + table: `001_create_users.sql`
- Never modify a migration after it has been merged — create a new one instead
- Applied on service startup before the Express app starts accepting requests

## 8. Folder Structure

Every Node.js service follows this layout:

```
src/
  index.ts          ← entry point: starts the server
  app.ts            ← Express app setup: middleware, routes, error handler
  routes/           ← one file per resource: users.ts, tasks.ts, health.ts
  middleware/        ← reusable middleware: auth.ts, logger.ts, errorHandler.ts
  db/
    pool.ts         ← pg Pool singleton
    migrations/     ← SQL migration files (001_create_users.sql, ...)
  types/            ← shared TypeScript interfaces and types
  __tests__/        ← integration tests
```

**Rules:**
- One route file per resource — never combine unrelated routes in one file
- `app.ts` configures middleware and mounts routes — never imports `pg` directly
- `pool.ts` is the only file that creates the database connection

## 10. Request Logging

Every service logs every inbound request using **Morgan**:

```
npm install morgan @types/morgan
```

Format: `[timestamp] METHOD /path → STATUS (Xms)`

```ts
// In app.ts
import morgan from 'morgan';
app.use(morgan('[:date[iso]] :method :url → :status (:response-time ms)'));
```

**Rules:**
- Morgan is mounted BEFORE route handlers — it logs every request including 4xx/5xx
- Do not log request bodies — they may contain passwords or tokens

## 11. Dockerfile Standard

Every service Dockerfile uses this exact multi-stage pattern:

```dockerfile
# Stage 1 — build TypeScript
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2 — production image
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
EXPOSE <PORT>
USER node
CMD ["node", "dist/index.js"]
```

**Rules:**
- `npm ci` — never `npm install` — ensures lockfile versions
- `USER node` — never run as root inside the container
- `EXPOSE` must match the service's `PORT` env var (3001, 3002, 8080)
- `--omit=dev` removes devDependencies from the production image

## 12. Testing Standard

**Framework:** Jest + Supertest for Node.js services. Vitest + React Testing Library for frontend.

**Rules:**
- Tests run against a **real test database** — never mock the database driver
- One test file per resource in `__tests__/` directory
- Every endpoint has at least: one success test + one error test
- Test database is separate from development database — use `TEST_DATABASE_URL` env var
- Setup: truncate tables before each test (not drop/recreate — too slow)
- Tests must pass in CI — `npm test` is a required CI step

**Test database setup pattern:**
```ts
// In __tests__/setup.ts
beforeEach(async () => {
  await pool.query('TRUNCATE users RESTART IDENTITY CASCADE');
});
afterAll(async () => {
  await pool.end();
});
```

## 13. Cross-Service ID Rule

When a service stores a reference to an entity owned by another service:
- Store the entity's **UUID only** — plain string column, no FK constraint
- Never join across service databases
- Never call another service's database directly

```sql
-- Correct: UUID stored as plain column, no REFERENCES constraint
assignee_id UUID NOT NULL,   -- refers to users.id in users_db — no FK

-- Wrong: cross-service FK — breaks service independence
assignee_id UUID REFERENCES users_db.users(id)  -- ← NEVER do this
```
