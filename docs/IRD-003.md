# IRD-003 — API Gateway & Infrastructure

**Scope:** Request routing, JWT validation middleware, Docker Compose stack, environment configuration, and non-functional requirements that apply to ALL services.  
**Linked DOP:** DOP-001 (all acceptance criteria — gateway is the entry point for every one)  
**Depends on:** IRD-001 (user-service), IRD-002 (task-service)  
**Note:** This IRD covers cross-cutting concerns. Every service must comply with the NFR section below, regardless of which IRD defines that service.

---

## What the gateway does

The api-gateway is the only component exposed to the outside world. It:
1. Receives all client requests on port 3000
2. Validates the JWT on every protected route
3. Injects `X-User-Id` and `X-User-Role` headers for downstream services
4. Forwards the request to the correct service via HTTP proxy
5. Returns the downstream response to the client unchanged

The gateway does not own any business data. It does not touch the database.

## Environment variables

```env
# .env (gitignored)
PORT=3000
USER_SERVICE_URL=http://user-service:3001
TASK_SERVICE_URL=http://task-service:3002
JWT_SECRET=replace_with_a_long_random_string_minimum_32_chars
```

> `JWT_SECRET` must be the **same value** as in user-service. Manage it as a single secret in production (Docker secret or environment injection). Never hardcode it.

## Routing table

| Method + Path | Forwards to | Auth required |
|---|---|---|
| `POST /users` | user-service | No |
| `POST /auth/login` | user-service | No |
| `GET /health` | (gateway responds directly) | No |
| `GET /tasks` | task-service | Yes |
| `POST /tasks` | task-service | Yes |
| `GET /tasks/:id` | task-service | Yes |
| `PATCH /tasks/:id/status` | task-service | Yes |
| `POST /tasks/:id/comments` | task-service | Yes |
| Any other path | 404 `{ "message": "not found" }` | — |

## JWT validation middleware

Applied to all routes marked `Auth required = Yes`.

```
1. Read Authorization header: "Bearer <token>"
2. If header missing or not "Bearer ..." → 401 { "message": "authorization header required" }
3. Verify JWT signature using JWT_SECRET
4. If signature invalid or token expired → 401 { "message": "invalid or expired token" }
5. Extract payload: { userId, email, role }
6. Attach to request:
     X-User-Id:   payload.userId
     X-User-Role: payload.role
7. Forward the request to the downstream service
```

The downstream service trusts `X-User-Id` and `X-User-Role` unconditionally — the gateway is the single point of auth enforcement.

## Docker Compose specification

File: `docker-compose.yml` at repo root.

```yaml
# docker-compose.yml
services:

  api-gateway:
    build: ./api-gateway
    ports:
      - "3000:3000"          # only service with a host port
    env_file: ./api-gateway/.env
    depends_on:
      user-service:
        condition: service_healthy
      task-service:
        condition: service_healthy
    networks:
      - app-net

  user-service:
    build: ./user-service
    env_file: ./user-service/.env
    depends_on:
      db-user:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3001/health"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - app-net

  task-service:
    build: ./task-service
    env_file: ./task-service/.env
    depends_on:
      db-task:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3002/health"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - app-net

  db-user:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: users_db
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: app_pass
    volumes:
      - db-user-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d users_db"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks:
      - app-net

  db-task:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: tasks_db
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: app_pass
    volumes:
      - db-task-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d tasks_db"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks:
      - app-net

volumes:
  db-user-data:
  db-task-data:

networks:
  app-net:
    driver: bridge
```

**Rules:**
- Named volumes (`db-user-data`, `db-task-data`) ensure database data survives `docker compose down`. Only `docker compose down -v` deletes the data.
- No service exposes a port to the host except api-gateway on 3000. Databases are internal only.
- `depends_on` with `condition: service_healthy` ensures services only start after their database is ready.

## Dockerfile standard (applies to all services)

Every service's Dockerfile must follow this pattern:

```dockerfile
# Example: user-service/Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
EXPOSE 3001
USER node
CMD ["node", "dist/index.js"]
```

**Rules:**
- Multi-stage build: build stage compiles TypeScript, production stage runs compiled JS only
- `USER node` — never run as root inside the container
- `npm ci` — not `npm install` — ensures exact lockfile versions
- `EXPOSE` must match the service's `PORT` env var

## Non-functional requirements (all services)

These requirements apply to every service in the project, regardless of which sprint.

| # | Requirement | Rule |
|---|---|---|
| NFR-01 | Health check | Every service has `GET /health` → `200 { "status": "ok", "service": "<name>" }`. No auth required. |
| NFR-02 | Configuration | Zero hardcoded config. All secrets, URLs, and ports via environment variables. `.env` is gitignored. `.env.example` is committed. |
| NFR-03 | Error response format | All error responses: `{ "message": "human-readable string" }`. No stack traces, no internal paths in production responses. |
| NFR-04 | Request logging | Every inbound request logged: `[timestamp] METHOD /path → STATUS (Xms)`. Use Morgan or equivalent. |
| NFR-05 | Port discipline | Only the gateway exposes a host port. All other services communicate on the internal Docker network only. |
| NFR-06 | Containerization | Every service has a Dockerfile. `docker compose up` from repo root starts the complete stack. |
| NFR-07 | Testing | At least one integration test per endpoint, running against a real test database (not mocked). Tests must pass in CI. |
| NFR-08 | Database migrations | Schema changes in versioned SQL files under `db/migrations/`. Applied on service startup. Never modified after merge. |
| NFR-09 | No shared databases | Each service has its own database. No service reads or writes another service's database. |
| NFR-10 | Cross-service IDs | When a service stores a reference to an entity owned by another service, it stores only the UUID. No foreign keys across service boundaries. |
