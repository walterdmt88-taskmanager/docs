# DOP-001 — Task Management System

**Type**: Product-level DOP  
**Area**: Capstone — Task Management System  
**Status**: Active  
**Owner**: thai_dm (Walter) · chau_tv  
**Sprints**: Sprint 1 (Day 9–11) · Sprint 2 (Day 12–14)

---

## Objective

Teams tracking tasks in chat tools (Slack, Discord) lose context, ownership, and visibility into what is blocked or overdue. This system gives teams a central REST API and web UI to create, assign, and track tasks with a clear audit trail of who did what and when.

---

## Goals

1. A team member can register, log in, and manage tasks entirely through the REST API
2. A team lead can view and filter all tasks across the system regardless of assignee
3. All services run as Docker containers and start with a single `docker-compose up`
4. A new engineer can clone the repo and run the full stack locally in under 5 minutes
5. The web UI allows non-technical users to perform all task operations without API calls

---

| JWT expiry enforcement | Token rejected after 24h — 401 returned |
| Error format compliance | 100% of error responses use `{ "error": "..." }` |

## Scope

### In Scope
- user-service: registration, login, JWT issuance
- task-service: task CRUD, status transitions, comments
- api-gateway: JWT validation, routing, CORS
- frontend-service: React SPA (Sprint 2)
- notification-service: async Discord notifications via Redis Streams (Sprint 3)
- Redis: event stream broker for task events
- Docker Compose: full-stack local deployment

### Out of Scope
- Email verification and password reset
- Real-time notifications (WebSocket / SSE)
- File attachments
- Cloud deployment, Kubernetes, Terraform

## Users and Use Cases

### Team Member
| Use case | Description |
|---|---|
| Register | email + password + full_name → user account |
| Log in | credentials → JWT token |
| Create a task | title, description, assignee → task saved |
| Update task status | todo → in_progress → done |
| Add a comment | text comment on any task |
| View my tasks | list tasks assigned to me, filterable by status |
| Web UI — all above | same operations via browser forms |

### Team Lead — extends Team Member
| Use case | Description |
|---|---|
| View all tasks | list all tasks, filter by status or assignee |
| View overdue tasks | tasks still todo/in_progress past due date |
| Dashboard | all tasks across assignees with status filters |

## Services and Ownership

| Service | Owns | Exposes |
|---|---|---|
| user-service | user accounts, credentials, JWT issuance | POST /users, POST /auth/login |
| task-service | tasks, status, comments | CRUD /tasks, POST /tasks/:id/comments |
| api-gateway | routing, JWT validation, CORS | all client-facing routes |
| frontend-service | compiled React SPA (static files) | port 3000 via nginx |
| notification-service | Discord notifications via Redis Streams | GET /health only (background consumer) |

**Rule:** all client requests go through api-gateway. Services do not expose ports externally.
`notification-service` receives no client traffic — it is a pure background event consumer.

---

## Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-01 | Every service exposes `GET /health → 200 { "status": "ok" }` |
| NFR-02 | All error responses use `{ "error": "string" }` — no other format |
| NFR-03 | Secrets via `.env` (gitignored) + `.env.example` (committed, no values) |
| NFR-04 | JWT validated only in api-gateway — never in user-service or task-service |
| NFR-05 | Status transitions: TODO→IN_PROGRESS→DONE (terminal), any→CANCELLED (terminal) |
| NFR-06 | Cross-service references are plain UUIDs only — no foreign keys across DBs |

## Acceptance Criteria

| ID | Given | When | Then | Pass signal | Fail signal |
|---|---|---|---|---|---|
| AC-01 | New user provides valid email, password, full_name | POST /users | 201, response has id/email/full_name/role/created_at, no password_hash | Status 201, no password_hash in body | 400/500, or password_hash present |
| AC-02 | Registered user provides correct credentials | POST /auth/login | 200, signed JWT with userId, expires 24h | Status 200, token decodes with userId + role | 401 on valid credentials |
| AC-03 | Authenticated user provides title, description, assignee_id | POST /tasks | 201, full task object, status=todo | Status 201, status field = "todo" | 400/500, or status missing |
| AC-04 | Authenticated user provides valid status | PATCH /tasks/:id/status | Task updated; invalid status returns 400 with valid values listed | Valid → 200; invalid → 400 with message | Invalid status accepted, or no message |
| AC-05 | Authenticated user provides comment text | POST /tasks/:id/comments | 201, comment saved and returned | Status 201, comment body in response | 400/500 or empty response |
| AC-06 | Authenticated member requests their tasks | GET /tasks?assignee=me | All tasks assigned to caller, ordered by created_at desc | Only caller's tasks returned | Other users' tasks appear in list |
| AC-07 | Authenticated team lead requests all tasks | GET /tasks | All tasks returned; member without filter gets only own tasks | Lead: all tasks; member: own only | Member sees all tasks without filter |
| AC-08 | Registered user opens web app | Visit /login, submit credentials | Authenticated, JWT stored, redirected to dashboard | Redirect to dashboard occurs, token in localStorage | Login fails or no redirect |
| AC-09 | Authenticated user opens dashboard | Page loads at / | Assigned tasks listed with status badges, created_at desc | Tasks visible with badges | Blank page or missing status badges |
| AC-10 | Authenticated user fills create-task form | Submit title + description + assignee | Task created, list refreshes, new task at top | New task appears at top of list | No refresh or task missing |
| AC-11 | Authenticated user on task detail page | Select new status | Status updated immediately; invalid transition shows error | UI reflects new status instantly | No update or error on valid transition |
| AC-12 | Authenticated user on task detail page | Submit comment form | Comment appears without full page reload | Comment in list, no full reload | Page reloads or comment missing |
| AC-13 | Authenticated team lead on dashboard | Apply assignee or status filter | List refreshes to matching tasks only | Filtered list shows correct subset | Filter has no effect |
| AC-14 | Any user creates a task, updates its status, or adds a comment | Operation completes via API | Discord notification appears in #task-alerts within 5 seconds | Discord message received with correct title and fields | No message, wrong channel, or delay > 5s |

## Non-Goals

- Production cloud deployment (AWS, GCP, Kubernetes)
- Real-time push to browser (WebSocket, SSE)
- Email notifications or verification
- Multi-tenancy beyond role-based access (member vs lead)
