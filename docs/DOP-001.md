# DOP-001 — Task Management System

> **DOP = Definition of Product.** This document answers: *What are we building and why?*
> Replace every section below with your group's project. Keep the structure.

---

## Problem statement

Teams tracking tasks in chat tools (Slack, Discord) lose context — tasks get buried in messages, ownership is unclear, and there is no way to see what is blocked or overdue. This system gives teams a central place to create, assign, and track tasks via a REST API, with a clear audit trail of who did what and when.

---

## Users and use cases

### Team Member
The primary user. Creates tasks, gets assigned tasks, updates task status.

| Use case | Description |
|---|---|
| Register an account | Provide email + password → receive a user account |
| Log in | Provide credentials → receive a JWT token |
| Create a task | Provide title, description, assignee → task is saved |
| Update task status | Move a task from `todo` → `in_progress` → `done` |
| Add a comment | Attach a text comment to any task |
| View my tasks | List all tasks assigned to me, filterable by status |

### Team Lead
Extends Team Member. Has read access to all tasks regardless of assignee.

| Use case | Description |
|---|---|
| View all tasks | List all tasks in the system, filter by status or assignee |
| View overdue tasks | List tasks still `todo` or `in_progress` past their due date |

---

## Services and ownership

Each service owns its data completely. No service reads another service's database directly.

### user-service
**Owns:** user accounts, credentials, JWT issuance  
**Does NOT own:** tasks, comments, or any application data  
**Exposes:** `POST /users` (register), `POST /auth/login` (login)

### task-service
**Owns:** tasks, task status, task comments  
**Does NOT own:** user profiles (stores only `user_id` references)  
**Exposes:** full CRUD on `/tasks`, `POST /tasks/:id/comments`

### api-gateway
**Owns:** routing, JWT validation middleware  
**Does NOT own:** any business data — it delegates to services  
**Rule:** all client requests go through the gateway. Services do not expose ports to the outside directly.

## Acceptance criteria

Each criterion is the source for one User Story in the sprint backlog.

| ID | Given | When | Then |
|---|---|---|---|
| AC-01 | A new user provides a valid email and password | They call `POST /users` | A user account is created. The response includes the user's `id` and `email`. Status 201. |
| AC-02 | A registered user provides correct credentials | They call `POST /auth/login` | A signed JWT is returned with `userId` in the payload. Expires in 24h. Status 200. |
| AC-03 | An authenticated user provides title, description, and `assignee_id` | They call `POST /tasks` | A task is created with status `todo`. The response includes the full task object. Status 201. |
| AC-04 | An authenticated user provides a valid `status` value | They call `PATCH /tasks/:id/status` | The task status is updated. Invalid status values return 400 with a message listing valid values. |
| AC-05 | An authenticated user provides comment text | They call `POST /tasks/:id/comments` | The comment is saved and returned. Status 201. |
| AC-06 | An authenticated user requests their tasks | They call `GET /tasks?assignee=me` | All tasks assigned to the calling user are returned, ordered by `created_at` desc. |
| AC-07 | An authenticated team lead requests all tasks | They call `GET /tasks` | All tasks in the system are returned. Non-leads calling this endpoint without filters get only their own tasks. |

## Out of scope (Day 8–11)

These are explicitly excluded from the first sprint to keep the scope manageable:

- Email verification
- Password reset flow
- Real-time notifications (WebSocket)
- File attachments on tasks
- Frontend / UI — API only
